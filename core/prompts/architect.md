# 1. Core Data-Shaping Idioms

## 1A. Named Emits
Assigning a process call returns a **multi-channel object**, not a channel. Access the specific emit name from the TECHNICAL CONTEXT:
- ✗ `process_a(input_data)` / `process_a.out` / `process_a.mix(process_b)`
- ✓ `process_a(input_data.ready)` / `process_a.processed.mix(process_b.output)`

**Single unnamed emit exception:** `result = process_a(data).result` works when only one channel is emitted.

## 1B. `.out` Accessor
Without assignment: `process_a(data, config)` → access via `process_a.out.result`
With assignment: `out_obj = process_a(data, config)` → access via `out_obj.result`

## 1C. Process Arity
Always match the `take:` signature from the TECHNICAL CONTEXT. Pay close attention to how many channels a tool requires.
```groovy
tool_single(flatTuple)           // 1 arg
tool_dual(data, reference)       // 2 args
tool_multi(data, config, extra)  // 3 args
```

## 1D. Static Value Injection
Define constants in `globals`, attach with `.multiMap` to combine with streams:
```groovy
data_stream.multiMap {
    data: it
    config: [ configCode, file(configPath) ]
}.set { prep }
tool_dual(prep.data, prep.config)
```

## 1E. Channel Combinations
- Use `.cross()` when matching items by a shared key.
- Use `.combine()` for Cartesian products or global shared references.
- Use `.mix()` to merge parallel streams of identical structures.

## 1F. Pre-Shaped Data
If data was already joined upstream, do **not** `.cross()`/`.combine()` again. Pass directly.

# 3. Globals vs Entrypoint

**`globals`** — static constants only. Always quote values.
- ✓ `{"type":"def", "name":"refCode", "value":"'CONFIG_X1'"}`
- ✗ `{"type":"def", "name":"input_stream", "value":"my_active_channel()"}` — **crashes Nextflow**

**`entrypoint`** — instantiate ALL active channels here: `my_active_channel()`, `get_dataset()`, etc.

---

# 4. Scoping & Emit Rules

- Sub-workflows are **isolated** — they cannot see entrypoint variables.
- Every `take_channels` entry **must** appear in `body_code`.
- `emit_channels`: only variable names or property assignments. No function calls.
  - ✓ `["result = mapper_res.result"]` (Direct extraction in emit)
  - ✗ `["out = process_data_mapper(data, config)"]`
- **NO POINTLESS `.set` ALIASING**: Do NOT use `.set {}` just to rename a process output so you can emit it. Handle the extraction directly in the `emit_channels` JSON list!
  - ✗ `body_code`: `analysis_out.report_file.set { report_file }`, `emit_channels`: `["report_file"]`
  - ✓ `body_code`: `analysis_out = my_process(...)`, `emit_channels`: `["report_file = analysis_out.report_file"]`
- Emit **what you defined**. If you created `prepared_data` via `.map`, emit that — not the raw input.
- **Terminal sub-workflows** (final step): `emit_channels` must be `[]`.
- **Void tools**: never assign to variable, never emit.
  - ✓ `process_final_report(result)`
  - ✗ `res = process_final_report(result)`
- **No active channels** (`my_active_channel`, `get_dataset`, etc.) inside sub-workflows. Entrypoint only.

---

# 5. Pipeline Design Rules

- **Group** related steps into cohesive sub-workflows (e.g., `data_pipeline`).
- **No single-process wrappers**: if a step is one tool, call it directly in the entrypoint.
- **NO CATALOG EVASION**: You MUST use the exact component IDs provided by the Consultant and investigate them with `check_component_channels`. Do NOT write an `inline_process` to reinvent an existing tool just to save a tool call.
- **No double shaping**: if Workflow A already crossed data+config, Workflow B must not cross again.
- **One shaping strategy** per data stream — either local (inside sub-workflow) or global (prepare_inputs). Not both.
- **Entrypoint** = orchestrator only. Instantiate channels, connect modules. Cannot emit.
- **QC tools**: use `qc_report1(data)`, `qc_report2(data)`, `qc_report3(results)` as-is. These are void.
